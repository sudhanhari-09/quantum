R1. Backend is the single source of truth for authentication, authorization,
    communication state, QKD results, QBER, key status, security decisions,
    attack detection and message delivery. Frontend renders only what the
    backend returns.
R2. No hard-coded or fake production data. Every rendered number comes from
    database-backed APIs or WebSockets. Seed data (if any) is stored in the
    database through normal code paths and never returned as static literals.

    names (Section 8), protocol names (Section 13), security status values,
    message status values, QBER semantics and error codes are identical in
    both tracks. Both agents implement Section 19 (API Contract) and Section
    20 (WebSocket Contract) without deviation.
R4. No Blockchain, physical quantum hardware, voice/video, social media, chat
    features, extra attack types (only INTERCEPT_AND_RESEND in v1), unnecessary
    AI models, microservices or cloud infrastructure.
R5. Any requirement not defined in the specification is tagged [TBD] with a
    recommended default. Do not silently invent requirements.
R6. QKD secret keys are never returned to the frontend in any REST or WS
    payload. Encryption uses a standard cryptographic library only.
R7. QBER is always computed from actual simulated QKD run data persisted in
    the database. It is never supplied or interpreted by the frontend.

SECTION 01 - PROJECT OVERVIEW
================================================================================
Quantum Secure Communication Platform (QSC) is a software-only simulation of
how Quantum Key Distribution (QKD), AI-driven protocol selection, standard
cryptographic encryption and eavesdropping detection combine to provide
secure user-to-user messaging. No physical quantum hardware is involved.

The simulation delivers:
- Secure registration + login with role-based access and unique QSC IDs.
- Sender-to-receiver secure messaging governed by a backend state machine.
- AI protocol recommendation engine that dynamically selects the QKD
  protocol to execute (recommendation == execution invariant).
- BB84 QKD simulation engine: ephemeral qubits, random bits, basis sets,
  measurement, basis comparison, sifting, error counting, QBER.
- Configurable security threshold; the Security Engine alone decides key
  acceptance/rejection and message blocking.
- Standard-library encryption AFTER key acceptance; never before.
- Eve (ATTACKER) intercept-and-resend attack simulation that actually
  modifies the QKD run internals so QBER rises and detection fires.
- Persistent storage: users, messages, communication sessions, QKD sessions,
  attacks, security reports, audit logs plus recommended supporting tables.
- Real-time WebSocket events for communication and attack state changes.
- Admin monitoring, protocol analytics, audit logs, per-role history.

Both agents follow Sections 17-18 phase plans and MUST build against the
shared contracts in Sections 4-16 and 19-21 so the two tracks integrate.

KEY DEFINITIONS (shared vocabulary - use exact strings everywhere)
- QSC ID      : unique public user id, format QSC-[A-Z0-9]{10}, generated
                and enforced by backend only, unique-constrained in DB.
- COMMUNICATION: one sender->receiver message attempt + lifecycle; stored in
                communication_sessions.
- QBER         : quantum bit error rate = differing_bits / compared_bits,
                computed from ACTUAL stored QKD run results (never static).
- THRESHOLD    : configurable simulation security threshold, default 0.11;
                stored per protocol. Never represented as a universal
                real-world QKD limit; UI must label it "simulation threshold".
- KEY STATUS   : PENDING | ACCEPTED | REJECTED.
- MESSAGE STATUS: PENDING | VERIFIED | PROCESSING | ENCRYPTED | DELIVERED |
                READ | REJECTED | BLOCKED | FAILED (mapping in Section 08).
- ATTACK TYPE  : INTERCEPT_AND_RESEND (only one in v1).
- EVENT        : {type, communication_id, state, actor_role, payload,
                timestamp} - identical shape on WS and diagnostics.

SECTION 03 - SCOPE
================================================================================
IN SCOPE: all functionality described in Sections 01-02 and detailed in
Sections 04-16, including user/system dashboards, QKD engine, AI recommender,
Eve simulation, security engine, reports, history, admin monitoring, realtime
events, persistence, tests and security controls.

OUT OF SCOPE (never add): Blockchain; physical quantum hardware; voice calls;
video calls; social media; chat features; attacks beyond
INTERCEPT_AND_RESEND; unnecessary AI models; microservices; cloud
infrastructure.

SIMULATION HONESTY: "Quantum" operations are classical Monte-Carlo
simulations of measurement statistics. All UI and API text must describe
operations as simulated, e.g., "simulated intercept-and-resend on the
idealized channel". The platform must never claim physical interception.
IN-SCOPE EXCEPTION: only BB84 is mandated as runnable in v1; other protocols
exist as registered-but-unsupported stubs (B21).

SECTION 04 - ROLES
================================================================================
Three roles enforced by backend JWT claims AND by frontend route guards.
The frontend hides UI but never trusts it; the backend rejects cross-role
access with HTTP 403 + error code ROLE_FORBIDDEN.

4.1 USER (role "USER")
- Can: register; login; obtain unique QSC ID; search users by QSC ID; create
  a secure message to a registered user; view own communication status,
  inbox, sent messages, communication history, security reports, profile.
- Cannot: access other users' messages/keys/threat data; view QBER or security
  decisions of sessions they do not own; act as attacker.

4.2 ATTACKER / EVE (role "ATTACKER")
- Can: login with attacker credential (created by admin); view ELIGIBLE ACTIVE
  communication sessions (metadata only: communication_id, sender name,
  receiver name, protocol, state, timestamps); choose a target; choose attack
  type + strength; launch the attack simulation; view attack progress/result;
  view own attack history.
- Cannot: read message plaintext or ciphertext; read user passwords; access
  secret keys; modify the database directly; change protocol configuration;
  access other users' private data; decrypt/read the receiver's message.
- Enforcement: every EVE-scoped endpoint builds responses WITHOUT sensitive
  fields by construction (use dedicated response models, never reuse full
  message/session schemas).

4.3 ADMIN (role "ADMIN")
- Can: list/manage users; create/manage attacker accounts; view communication
  statistics, security events, attack activity, protocol statistics, audit
  logs; monitor platform activity.
- Cannot: view decrypted message content (no role can; no endpoint returns
  plaintext to anyone); alter simulation facts; only configure global
  settings (threshold, protocol config) through dedicated admin endpoints.

RESPONSE MODEL RULE: a shared "visibility matrix" in the backend maps each
resource (user, message, session, qkd, attack, report, audit) to what each
role may see. Route handlers apply it before serialization. Frontend also
implements guards (F4) but the matrix is the source of truth.

in backend services; SQLAlchemy ORM persists to PostgreSQL (prod) or SQLite

backend services to the appropriate audiences.

LAYERS
- Frontend (Track A): public zone, USER zone, ATTACKER zone, ADMIN zone;
  Axios client; TanStack Query caches; Zustand store; wsClient wrapper;
  route guards; per-role layouts.
- API (Track B): FastAPI routers (auth, users, messages, communications,
  qkd, security, attacks, reports, analytics, admin, audit, ws). Middleware:
  JWT auth, role enforcement, CORS, rate limiting, request-id, error handler.
- SERVICES (Track B): Authentication, User, Messaging, CommunicationSession,
  StateMachine, QKDEngine, AIRecommendation, AttackSimulation, SecurityEngine,
  Encryption, Inbox/Delivery, Reporting, Admin, Audit, Realtime, Config.
- PERSISTENCE: tables in Section 11 via SQLAlchemy repositories.
  (A per-service repository pattern keeps services testable.)

DATA FLOW PICTURE (one message)
  UI(compose) -> POST /messages -> MessagingService ->
  SessionService (CREATED) + StateMachine -> AIRecommender (PROTOCOL_SELECTED)
  -> QKDEngine runs recommended protocol -> QBER computed ->
  SecurityEngine decides -> Encryption OR Blocking -> Inbox/Delivery ->
  ReportService + AuditService -> RealtimeService broadcasts -> WS -> UI.

FAILURE CONTRACT: any service exception becomes a typed API error envelope
{code,message,details} via a single global exception handler; the frontend
maps codes to UI states (see Section 19 error table).

SECTION 07 - CORE WORKFLOW (END TO END, NORMAL PATH)
================================================================================
Implemented by backend orchestration (B12-B26) and mirrored by the frontend
wizard (F8-F18). Steps and their state transitions (Section 08):

STEP 1  USER registers -> POST /auth/register -> unique QSC ID assigned.
STEP 2  USER logs in -> POST /auth/login -> access JWT + profile.
STEP 3  SENDER searches -> GET /users/search?qsc_id= -> receiver verified;
        state CREATED -> RECEIVER_VERIFIED (or 404 USER_NOT_FOUND).
STEP 4  SENDER composes -> POST /messages {receiver_qsc_id, content}.
STEP 5  Backend creates MESSAGE + COMMUNICATION_SESSION (state CREATED);
        validates receiver exists and != sender (409 SELF_DELIVERY).
STEP 6  AI: AIRecommendationService evaluates features (Sec 12); stores
        ai_recommendations row; session.protocol set to recommended protocol;
        state AI_ANALYZING -> PROTOCOL_SELECTED.
STEP 7  QKD: QKDEngine executes EXACTLY the recommended protocol (invariant).
        state QKD_INITIALIZING -> QKD_RUNNING (leases qkd.progress) ->
        KEY_SIFTING -> QBER_EVALUATION (QBER from run results, Sec 13).
STEP 8  Security: SECURITY_CHECK -> if qber<=threshold KEY_ACCEPTED
        (key persisted encrypted at rest), else ATTACK_DETECTED.
STEP 9  ENCRYPTING: EncryptionService AES-GCM with HKDF(key); plaintext is
        NEVER stored; only ciphertext + nonce + tag.
STEP 10 ENCRYPTED -> DELIVERED: message appears in receiver inbox.
STEP 11 Receiver opens -> message.decrypted on-the-fly (key stays server-side)
        -> READ. A security_report row is written (both paths) and events
        emitted (message.encrypted|delivered|read + security.*).

ATTACK PATH (parallel, Sec 14):
EV1 EVE logs in -> GET /communications/active (eligible states below).
EV2 EVE selects target; POST /communications/{id}/attacks with
    {attack_type: INTERCEPT_AND_RESEND, attack_strength: p}.
EV3 AttackSimulation reruns/annotates the target QKD run: it intercepts
    round(p * qubits) simulated qubits, measures each in a random basis,
    resends the measured result; the stored run data is updated so the error
    counters change, QBER is recomputed, and SecurityEngine re-evaluates.
EV4 If recomputed QBER > threshold: attack.detected, KEY_REJECTED, message
    BLOCKED (never in inbox as delivered), attack row + audit + report.
EV5 If still <= threshold: attack not detected; session resumes.

ATTACK WINDOW: sessions eligible when state in {QKD_INITIALIZING,
QKD_RUNNING, KEY_SIFTING, QBER_EVALUATION, SECURITY_CHECK}. Once KEY_ACCEPTED,
attacks return 409 ATTACK_WINDOW_CLOSED.

NORMAL-PATH DELIVERIES ARE THE ONLY WAY MESSAGES APPEAR IN AN INBOX.
BLOCKED messages never appear as delivered to the receiver.

SECTION 08 - COMMUNICATION STATE MACHINE
================================================================================
Backend-owned state machine. communication_sessions.session_status is set
ONLY by the StateMachineService, which holds a validated transition table;
any illegal transition returns HTTP 409 with code INVALID_STATE_TRANSITION.

STATES (fixed vocabulary; frontend renders EXACTLY these strings)
  CREATED, RECEIVER_VERIFIED, AI_ANALYZING, PROTOCOL_SELECTED,
  QKD_INITIALIZING, QKD_RUNNING, KEY_SIFTING, QBER_EVALUATION,
  SECURITY_CHECK, KEY_ACCEPTED, ENCRYPTING, ENCRYPTED, DELIVERED, READ,
  ATTACK_DETECTED, KEY_REJECTED, BLOCKED.
  [REC extra state] FAILED (terminal, internal-error path).

LEGAL TRANSITIONS (tests assert each; everything else rejected)
  CREATED -> RECEIVER_VERIFIED
  RECEIVER_VERIFIED -> AI_ANALYZING
  AI_ANALYZING -> PROTOCOL_SELECTED
  PROTOCOL_SELECTED -> QKD_INITIALIZING
  QKD_INITIALIZING -> QKD_RUNNING
  QKD_RUNNING -> QKD_RUNNING              (progress steps; same state)
  QKD_RUNNING -> KEY_SIFTING
  KEY_SIFTING -> QBER_EVALUATION
  QBER_EVALUATION -> SECURITY_CHECK
  SECURITY_CHECK -> KEY_ACCEPTED | ATTACK_DETECTED
  KEY_ACCEPTED -> ENCRYPTING
  ENCRYPTING -> ENCRYPTED
  ENCRYPTED -> DELIVERED
  DELIVERED -> READ
  ATTACK_DETECTED -> KEY_REJECTED
  KEY_REJECTED -> BLOCKED
  QKD_INITIALIZING..SECURITY_CHECK -> ATTACK_DETECTED (attack path)
  Any pre-KEY_ACCEPTED state -> FAILED (terminal).
  Terminal states: READ, BLOCKED, FAILED (no outgoing edges).

GUARDS enforced by StateMachineService:
- Sequence guard: follow the table; no skipping.
- Ownership guard: only owning user services may advance their session;
  EVE never transitions states directly (AttackSimulationService asks the
  StateMachineService to move the session when the attack outcome is known).
- Attack-window guard: attack re-evaluation only while state in
  {QKD_INITIALIZING, QKD_RUNNING, KEY_SIFTING, QBER_EVALUATION,
  SECURITY_CHECK}; re-attack loop capped at MAX_REATTACKS=3 [REC].
- Atomicity: transition + row update + WS event + audit row happen in ONE
  DB transaction; audit records every transition (B32).

DERIVED STATUS MAPPING (used by all API responses; UI renders these)
  session_status        message.status  key_status
  CREATED               PENDING         PENDING
  RECEIVER_VERIFIED     VERIFIED        PENDING
  AI_ANALYZING/PROT_SEL PROCESSING      PENDING
  QKD_INIT..SECURITY    PROCESSING      PENDING
  KEY_ACCEPTED          PROCESSING      ACCEPTED
  ENCRYPTING/ENCRYPTED  ENCRYPTED       ACCEPTED
  DELIVERED             DELIVERED       ACCEPTED
  READ                  READ            ACCEPTED
  ATTACK_DETECTED       REJECTED        REJECTED
  KEY_REJECTED/BLOCKED  BLOCKED         REJECTED
  FAILED                FAILED          PENDING

message.attack_detected=true whenever the path ends BLOCKED; stored on the
message row and reflected in reports.

WS NOTE: every transition emits event communication.state_changed with
payload {state, previous_state} so the UI timeline can animate (F10).

SECTION 12 - AI ARCHITECTURE (PROTOCOL RECOMMENDATION)
================================================================================
Purpose: dynamically evaluate communication conditions and choose which QKD
protocol executes. MUST be a real scoring engine, never hard-coded. v1 has
only BB84 enabled, but the engine still computes a full feature vector,
per-protocol scores, confidence and explanation from live inputs so the
"recommendation" is genuinely dynamic and future protocols slot in.

INPUT FEATURES (evaluated per message from real state):
  F1 channel_noise            float 0..1  -- simulated noise level from
                             ConfigService or per-session setting
  F2 security_requirement     LOW|MEDIUM|HIGH -- chosen at message creation
  F3 estimated_attack_risk    0..1 -- computed from recent detected attacks
                             (count_last_24h * decaying weight)
  F4 distance                 km (simulated route distance setting)
  F5 key_efficiency           expected sifted key rate of each protocol
  F6 protocol characteristics table (per protocol: noise_resistance,
                             rate, distance_suitability, maturity)
  F7 time_sensitivity         optional message flag default MEDIUM [TBD]
Feature values stored in ai_recommendations.features jsonb for audit.

SCORING MODEL [REC]
  score(P) = SUM over features w_i * normalized_value(P, F_i)
  Weights w_i live in protocol_configs.parameters.jsonb and are ADMIN
  editable (audited). Defaults:
     channel_noise          0.25
     security_requirement   0.25
     attack_risk            0.20
     distance               0.10
     key_efficiency         0.10
     maturity/reliability   0.10
  Per-protocol capability matrix (BB84 baseline; others stubs):
     BB84 : noise 0.11 | eff 0.9 | dist up to 100 | maturity 1.0
     B92  : [TBD] enrol later via registry
     E91  : requires entangled phase -- [REC] flag not_supported v1
  Confidence = softmax(top2 scores) or margin (top - runnerup)/top; MUST be
  computed, never hard-coded. Explanation = templated but driven by feature
  contributions (e.g., "BB84 chosen: highest maturity, meets target risk").
OUTPUT CONTRACT (stored in ai_recommendations + returned by
GET /communications/{id}/recommendation):
  {protocol: "BB84", confidence: 0.86, explanation: "...",
   scores: {"BB84":0.86,...}, features: {...}, evaluated_at: ts}

CRITICAL INVARIANT (R8 = Objective O6):
  The protocol string persisted to communication_sessions.protocol is the
  SAME string stored in ai_recommendations.protocol; QKDEngine receives
  session.protocol as its single input; any mismatch raises RuntimeError
  MISMATCH_RECOMMENDED_EXECUTED and fails the communication with FAILED
  (audited). Unit test asserts this invariant.
Frontend: F11 only RENDERS recommendation payload; never computes it.

SECTION 13 - QKD ARCHITECTURE
================================================================================
13.1 PROTOCOL REGISTRY [REQ]
  ProtocolBase (abstract): name, requires_entanglement flag, generate_qubits(),
  sift(), compute_qber(), estimate_key_efficiency().
  Registry `protocol_registry.register(Base)`; names: BB84, B92, E91,
  SIX_STATE, SARG04, DECOY_BB84. Only BB84 implements full run; others
  register but mark supported=False and return 501 when invoked. Adding a
  new protocol = add ONE module + register line (no core edits) (B21).

13.2 BB84 SIMULATION (B14) - deterministic-per-seed, default 256 qubits
  Steps:
   1. Alice random bits          a_bits[n] via secrets/SecureRNG
   2. Alice bases                a_bases[n] in {R(rectilinear/ Z), D(diag/ X)}
   3. Encode states classically  (bit,basis)->base state label; store sim
      eigenvector table
   4. Channel noise contribution: flip each transmitted bit w.p. channel_noise
      (default channel_noise=0.01) - configurable [REQ]
   5. Bob bases                  b_bases[n] random
   6. Bob measurement: if basis matches and no noise -> same bit; else
      probabilistic per measurement matrix (standard BB84 outcome rule)
   7. Basis comparison: keep indices where basis equal -> matching_bases count
   8. Sifting: matched bits -> sifted_bits bitstring; Bob's sifted also kept
   9. Error test: for random sample "compared_bits" (e.g. all sifted bits when
      small; or a sample subset) count differing -> errors
  10. QBER = errors / compared_bits; store ALL counters in qkd_sessions
  11. Key validation: QBER <= threshold (default 0.11) -> ACCEPTED else
      REJECTED; both values stored
  12. key_status saved onto session and message
  All randomness uses injected RNG for reproducible tests (seedable).

13.3 QBER (B16)
  QBER = errors / compared_bits. Both baseline (session-owned) and post-attack
  runs stored (is_baseline flag) so before/after compare works for Eve UI.
  IMPORTANT: threshold is SIMULATION threshold (default 0.11), explicitly
  labeled in API + UI as simulation threshold, never as universal physics.

13.4 KEY HANDLING (B18/B19)
  - Accepted key: 32-byte HKDF(sifted_bits || communication_id). Stored
    encrypted (secret_keys.row, AES-GCM w/ QSC_MASTER_KEY env). Both sides
    are the server in the simulation, so one record represents "shared".
  - Encryption: AES-GCM via `cryptography`; random 12-byte nonce; tag
    appended; stored base64 in messages.encrypted_message + messages.nonce.
  - Decryption only in EncryptionService on GET message detail for the
    receiver (or sender); key decrypted in-process, never leaves memory or
    API.
  - Rejected path never creates secret_keys row; encrypted_message remains
    null; message stays BLOCKED.

SECTION 14 - EVE ATTACK ARCHITECTURE
================================================================================
AttackSimulationService is the ONLY component allowed to run attacks. It is
purely simulated; every mutation is applied to stored simulation data so
QBER genuinely changes. All UI/API copy must use "simulated" language.

14.1 PARAMETERS
  target: communication id; attacker: authenticated role ATTACKER.
  Attack window states {QKD_INITIALIZING, QKD_RUNNING, KEY_SIFTING,
  QBER_EVALUATION, SECURITY_CHECK}; outside -> 409 ATTACK_WINDOW_CLOSED.
  attack_strength p in [0.1, 1.0] (fraction of transmitted qubits
  intercepted). attack_type must equal INTERCEPT_AND_RESEND (v1).

14.2 SIMULATED INTERCEPT-AND-RESEND ALGORITHM
  Input: the session's baseline qkd_sessions row (is_baseline=true). The
  QKDEngine persists counters plus the RNG seed for each run, so the engine
  can deterministically RERUN the run with Eve injected for attacks (seed =
  deterministic function of communication_id + run counter). This keeps
  results reproducible and QBER genuinely recomputed from rerun counters.
  Steps:
   1. n_intercepted = round(p * n_qubits)
   2. For each intercepted index i: Eve picks a random basis b_e, measures
      the simulated transmitted state in b_e -> outcome bit, and resends
      that outcome (in b_e) onward.
   3. Bob measures possibly-corrupted states using standard BB84
      measurement rules, producing the classic intercept-resend error
      signature (expected QBER_after ~ channel_noise + p * 0.25; this
      formula is a sanity bound only - the stored QBER MUST be computed
      from actual rerun counters to honor R7).
   4. Write NEW qkd_sessions row: is_baseline=false, modified counters,
      recomputed QBER.
   5. Persist attacks row: attacker_id, communication_id, attack_type,
      attack_strength p, states_intercepted (round(p*n)), states_modified
      (exact from rerun), qber_before (baseline), qber_after (new run),
      detection_status, created_at.
   6. Hand SecurityEngine the new QBER + active threshold.
   7. StateMachine transitions: DETECTED -> ATTACK_DETECTED ->
      KEY_REJECTED -> BLOCKED (message status BLOCKED; never in inbox as
      delivered). NOT_DETECTED -> session resumes current flow; attack
      is still recorded in attacks + audit + report.
  Determinism requirement: B23 unit tests MUST assert that rerunning with
  same seed yields identical counters.

14.3 EVE VISIBILITY (no leakage)
  Eve endpoints return only: communication_id, sender_name, receiver_name,
  protocol, session_status, created_at; after an attack also: attack_id,
  qber_before, qber_after, detection_status, states_intercepted,
  states_modified, attack_strength.
  Eve endpoints MUST NOT return: encrypted_message, nonce, plaintext, key
  material, threshold, emails, or any other user's QSC ID beyond the sender
  and receiver public names.

14.4 EVE HISTORY
  GET /api/v1/attacks/history returns only the authenticated attacker's own
  attacks, newest first.

SECTION 15 - SECURITY ARCHITECTURE
================================================================================
SecurityEngine is the sole authority for:
  - evaluating QBER against the active threshold (protocol_configs default,
    captured per run in qkd_sessions.threshold),
  - producing the key decision (ACCEPTED | REJECTED),
  - declaring detection (DETECTED | NOT_DETECTED),
  - granting or forbidding encryption and delivery.

DECISION MODEL (exact; unit-test these rules):
  if qber <= threshold:
     key_status = ACCEPTED; encryption allowed; delivery allowed.
  else:
     attack_suspected = true; key_status = REJECTED; encryption NOT
     allowed; delivery blocked (message status BLOCKED).
  On the attack path the engine re-evaluates with post-attack QKD results.
  A downgrade (ACCEPTED -> REJECTED) is allowed only while the session is
  still inside the attack window; once DELIVERED no downgrade.

ENCRYPTION GATE: EncryptionService must first obtain current
key_status=ACCEPTED from SecurityEngine; on REJECTED it raises
KEY_REJECTED and never encrypts. QKD generation and message encryption
remain separate modules (different files, different services).

DECRYPTION ACCESS:
  - GET message detail returns plaintext ONLY if requester is the receiver
    (or the sender viewing own sent message) AND message.status is
    DELIVERED or READ; key is loaded, deciphered in-process, response
    carries only plaintext; failures yield safe 403/404.

SAFE ERRORS: user-safe messages from a shared table; codes expose only a
taxonomy (USER_NOT_FOUND, ROLE_FORBIDDEN, INVALID_STATE_TRANSITION,
ATTACK_WINDOW_CLOSED, KEY_REJECTED, ...). Details go to server logs only.

SECTION 20 - WEBSOCKET CONTRACT
================================================================================
Transport: ws(s)://host/ws/... with ?token=<access_jwt> on connect. Server
validates JWT + role; rejects otherwise (close code 4401). Message envelope
(server -> client) is exactly:
  {"type": "event.type", "communication_id": 12 | null,
   "state": "<STATE>", "actor_role": "USER|ATTACKER|ADMIN|SYSTEM",
   "payload": {...}, "timestamp": "2026-08-22T10:15:00Z"}
Client -> server: {"action": "ping|unsubscribe_communication", ...}
Server heartbeats every 30s -> ping frame; client replies pong.

CHANNELS
  /ws/user/events            audience USER + ADMIN (user dashboard)
  /ws/communications/{id}    audience sender + receiver + ADMIN;
                             metadata-only for that session
  /ws/eve/events             audience ATTACKER (active sessions feed)
  /ws/admin/events           audience ADMIN (platform feed)

EVENTS (type names are stable identifiers; payloads are documented)
  communication.created      MUST HAVE  payload {communication_id, sender,
                             receiver, created_at} -> user/eve/admin
  communication.receiver_verified REQUIRED payload {receiver}
  communication.state_changed MUST HAVE  {state, previous_state}
  ai.analysis_started        RECOMMENDED
  ai.protocol_selected       MUST HAVE  {protocol, confidence,
                             explanation, scores}
  qkd.started                MUST HAVE  {protocol, qubit_count}
  qkd.progress               MUST HAVE  {percent, stage}
  qkd.completed              MUST HAVE  {qubits_generated, matching_bases,
                             sifted_bits, compared_bits, errors, qber}
  qber.calculated            MUST HAVE  {qber, threshold}
  security.check_started     RECOMMEND
  security.key_accepted      MUST HAVE  {message_id}
  security.key_rejected      MUST HAVE  {message_id, reason}
  attack.started             MUST HAVE  {attack_id, communication_id,
                             strength, states_intercepted}
  attack.progress            MUST HAVE  {percent, states_modified}
  attack.detected            MUST HAVE  {attack_id, qber_before, qber_after,
                             detection_status}
  message.encrypted          MUST HAVE  {message_id}
  message.delivered          MUST HAVE  {message_id, receiver_id}
  message.blocked            MUST HAVE  {message_id, reason}
  message.read               MUST HAVE  {message_id, read_at}
  audit.record               OPTIONAL   (admin channel only, throttled)
  config.updated             OPTIONAL   (admin channel)

SECTION 23 - TESTING STRATEGY

23.1 UNIT TESTS (backend pytest / frontend vitest)
  - Authentication: hashing verify, token issue/verify/expiry, refresh
    rotation, disabled user denial.
  - QSC ID: format, uniqueness (seeded 1000), collision retry.
  - BB84: known-answer vectors, basis matching distribution, noiseless
    == expected ratio; deterministic on seed.
  - QBER: 0..1 boundaries; zero-denominator guard.
  - Security decisions: qber<=t accepted, >t rejected, downgrade rules.
  - Encryption/decryption: round-trip, tamper detection, nonce uniqueness.
  - AI recommendation: score math, confidence bounds, invariant test.
  - Eve attack: rerun determinism, qber_after >= qber_before, strength
    effect monotonicity.
  - Visibility: schema-level tests (Eve responses contain no sensitive keys).

  - Send message -> session created -> recommendation -> executed protocol
    equality -> QKD run -> QBER -> security -> encrypted -> delivered -> read.
  - Attack flow: eve lists, attacks, qber changes, detected, key rejected,
    blocked, inbox absence.
  - Reports and history equality with source rows.

  - WebSocket: connect auth, event audience routing, disconnect cleanup.
